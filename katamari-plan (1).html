Who does what

Each person owns one Minimum, one A and one B requirement (Member 4 owns A3 and B2, the hardest one). Everyone comments their own code, writes their own log entries, films the video and presents their own part.

Day by day

About one day of work per task. How names the common/ functions to use (MV.js, initShaders, webgl-utils); everything else is plain WebGL and JavaScript. Git says which branch, what to commit, and whether the day ends with a push or a PR + merge. The duty person makes sure a meaningful commit reaches GitHub before midnight, but everyone commits every workday. Weekends are planned, lighter days (about half a day): if you can't work one, do that task first thing Monday and tell the team.

Blocked or finished early? In this order: review an open PR → comment and cite your own code → add a console test in tests/ → write your log entries → ask whoever is furthest behind what you can take (and log it).

Code rules

Files and owners

FileOwner

Only common/ libraries (MV.js, initShaders.js, webgl-utils.js). No three.js, no CDN, no copied helper files. Never edit common/. Images are assets: allowed, but cite source and licence.

Shared conventions

  • Y is up, ground is y = 0, units are metres, WORLD_R lives in config.js.
  • dt in seconds every frame, so speed doesn't depend on frame rate.
  • MV.js angles are degrees: rotate(deg, axis), perspective(fovyDeg, …).
  • Matrices: scalem, translate, rotate. mult(A, B) applies B first, so model = T · R · S.
  • flatten(m) already transposes, so pass false to uniformMatrix4fv.
  • normalMatrix(model, true) returns a mat3 for the shader.
  • normalize(v) changes v. Use normalize(vec3(v)) to keep the original, and check length(v) > 0 first.
  • Matrix × vector needs matching sizes: mult(orientation, vec4(offset, 0)).
  • Use WebGLUtils.setupWebGL, initShaders(gl, "vertex-shader", "fragment-shader") and requestAnimFrame from common/.
  • Textures: power-of-two sizes for mipmaps and REPEAT. Always test on localhost, never file://.

The Player interface (Member 2 owns it)

position: vec3        velocity: vec3        orientation: mat4 (accumulated, re-orthonormalized)
radius: core radius   totalVolume: number
attachments[]: { localOffset: vec3, radius, mesh, material, texture }   // in the katamari's local frame
effectiveRadius()          // cbrt(3 * totalVolume / (4 * PI)), used by camera and collisions
worldPositionOf(att)       // position + first 3 of mult(orientation, vec4(att.localOffset, 0))

Every requirement, five steps

  1. Start a branch from the latest main.
  2. Commit small working steps, push daily.
  3. Each morning, merge in main.
  4. Open a PR: what it does, how to test, any AI used.
  5. Teammate reviews within 24 h, then "Create a merge commit" and delete the branch.
# 1. start (example: Member 2, requirement A2)
git switch main
git pull
git switch -c a-keyboard-slide

# 2. commit small steps
git add js/Player.js
git commit -m "Player: exponential friction so the ball comes to rest (A2)"
git push -u origin a-keyboard-slide      # first time; afterwards just: git push

# 3. each morning
git fetch
git merge origin/main

# 4–5. open the PR on GitHub → review → "Create a merge commit" (never squash) → delete branch
# then everyone:
git switch main
git pull

Docs go straight to main. README.md (it must stay in the root, the brief requires the Developer Log there) and the docs/ folder (citation list, AI log details, video script) need no branch: git pull, edit, commit Docs: …, push right away. Code still always goes through a branch and PR.

Conflict? Fix it together with that file's owner, reload the game on localhost, then git add, git commit, git push. Never pick "accept mine" for a whole file and never git push --force.

Good and bad commits

Good: one working step, Area: what (req)

  • World: place spheres by rejection sampling, no overlaps (M1)
  • Collision: test sphere vs each attachment in world space (B2)
  • Docs: cite skybox texture source and licence

Bad: padding or unclear

  • update, fix, asdf, final2
  • a whole day's work in one commit
  • whitespace-only changes, or anything that breaks the page

Write code and its comments in the same commit. Commit from your own laptop and never for a teammate. Check GitHub → Insights → Contributors at every tag and rebalance early.
